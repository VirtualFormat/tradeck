A 股数据接入

唯一需要自己写的：openbb-akshare-provider

OpenBB 没有官方 AKShare Provider。需要写一个扩展（按 Fetcher 接口），注册后 provider="akshare" 即可用。工作量 2-3 天（学 Provider 开发 1 天 + 写 5-8 个 Fetcher 1-2 天）。这个扩展还可以开源给社区。

Tushare 可以走 FMP（FMP 覆盖 A 股主要标的），深度 A 股数据先用 AKShare 补，后续按需写 tushare Provider。

MCP Server 怎么接

MCP Server 不走 HTTP，直接 import OpenBB SDK（同进程，省网络开销）：

# mcp_server.py
from openbb import obb
from mcp.server import Server

@server.call_tool()
async def call_tool(name, arguments):
    if name == "get_quote":
        # 直接调 SDK，不走 HTTP
        result = await obb.equity.price.quote(
            symbol=arguments["symbol"],
            provider="fmp"  # 或 "akshare"
        )
        return [TextContent(type="text", text=result.model_dump_json())]

为什么不推荐 OpenStock

OpenStock 的三个硬伤

① AGPL-3.0 协议："作为 Web 服务部署"也必须开源。如果你未来想做"小范围公开平台"，AGPL 要求所有访问者能获取你的修改代码——这对"公开平台"是致命约束。

② 数据源硬编码 Finnhub + TradingView widget：TradingView 免费版对 A 股/港股支持差，且 widget 是嵌入式 iframe，数据不经过你的后端，无法和 OpenBB 数据层统一。

③ 换源成本巨大：OpenStock 的组件设计围绕 Finnhub 响应格式，换到 OpenBB REST API 要改几乎每个组件——工作量不比自建少。

为什么不推荐 OpenBB Terminal Pro

Terminal Pro 不适合的原因

① 闭源商业产品：无法定制 UI、无法嵌入自己的组件、无法和自建 MCP Agent 协同。

② 绑定 OpenBB 全栈：必须用 OpenBB 的数据/凭证/部署体系，无法换底座。

③ 定位机构用户：价格、复杂度、功能都按机构场景设计，个人/小团队用是大材小用。

它适合"机构内部部署给分析师用"，不适合你的场景。

自建前端的优势

为什么自建是更好的选择

① 数据层已省时间：用 OpenBB Platform 做后端，省了 2 周数据层工作，可以把时间投入到前端。

② 技术栈成熟：Next.js 15 + shadcn/ui + Tailwind v4 是 OpenStock 验证过的组合，开发体验好。

③ 完全可控：对接 OpenBB REST API、对接 MCP Agent 入口、加 A 股特色功能（龙虎榜/北向资金）都不受原项目约束。

④ 无协议风险：未来想做"小范围公开平台"或商业化，无 AGPL 约束。

⑤ 复用 tradeck 经验：你已有 React + Tailwind + react-grid-layout + TanStack Query 的经验（tradeck 项目），技术栈完全可迁移。

Qlib 深度分析

7.1 Qlib 的独特价值

Qlib 是唯一一个把 AI/ML 和量化研究全流程打通的开源平台。它的价值不在于回测（回测只是其一小部分），而在于：

AI 因子挖掘

内置 Alpha158（158 个经典因子）和 Alpha360（360 个）数据集，不用自己从零造因子

近期推出 RD-Agent：用 LLM 自动挖掘新因子和优化模型

ML Pipeline

20+ 预训练模型：LightGBM / XGBoost / LSTM / Transformer / GATs / HIST

从数据 → 特征 → 训练 → 预测 → 回测 → 评估，qrun 一键跑完整流程

7.2 Qlib 的局限

局限影响应对
A 股数据需自行接入 官方只提供 Yahoo，A 股要转 Qlib 格式 写一个 AKShare/Tushare → Qlib 的转换脚本（2-3 天）
学习曲线陡 需要 ML + 量化双背景 先用 vectorbt 跑通简单策略，Qlib 作为进阶
非实盘框架 不直接支持真实下单 本方案范围不含实盘，不是问题
Windows 兼容性差 部分依赖在 Windows 装不上 用 WSL/Docker（与 tradeck 现有开发环境一致）

7.3 是否引入 Qlib 的决策

决策：阶段性引入

阶段 2A-2C（前 3-4 周）：不引入 Qlib，用 vectorbt。先把策略验证和参数寻优跑通，验证研究思路。

阶段 2D（如需要）：引入 Qlib 做 AI 因子研究。此时已有数据底座和 Parquet 归档，Qlib 接入只需写一个数据转换层。

不强行一开始就用 Qlib：它的 ML pipeline 学习成本高，在还没明确研究方向时就引入会增加认知负担。

9.3 量化工具的特殊风险

⚠️ 量化回测的三大陷阱

1. 幸存者偏差：回测用的是"现在还存在的股票"，忽略退市股。应对：用 point-in-time 数据（Qlib 支持）。

2. 前视偏差：用了"未来才知道"的数据（如用年报发布日之前的财报数据）。应对：严格用发布日期而非报告期。

3. 过拟合：参数调到历史最优但对未来无效。应对：交叉验证 + 样本外测试 + 实盘小额验证。
