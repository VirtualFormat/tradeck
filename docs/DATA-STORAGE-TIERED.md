# 分层存储设计 — 全市场全标的数据落地（阶段四最终状态）

> 阶段四「加固」的正式设计。前提：数据服务拆分（阶段一~三）已完成验收，
> 本文档定义全市场全频率数据落地时的存储拓扑。PG 不被替换，只做加法。
> 上游方案见 `docs/DATA-SERVICE.md`；任务卡见 `plans/TASKS-DATA-SERVICE.md` 阶段四。

## 设计前提与量级测算

以现有 universe 为底（CN 5528 + HK 2841 + US 11645 ≈ 2 万标的）：

| 数据类型 | 行/日 | 行/年（250 交易日） | 单行长 | 年存储（未压缩） | 10 年 |
|---|---|---|---|---|---|
| 日K（现有） | 2 万 | 500 万 | ~90B | 0.5 GB | 5 GB |
| 分钟K（1min） | ~1000 万 | 25 亿 | ~60B | 150 GB | 1.5 TB |
| 逐笔/tick（若做） | 5000 万-1 亿 | 百亿级 | ~50B | TB 级 | 10TB+ |
| 技术指标（全市场） | 2 万 | 500 万 | ~250B | 1.2 GB | 12 GB |
| 基本面/快照类 | 万级 | 百万级 | — | <1 GB | 可忽略 |

**核心判断**：PG 的死穴不是日K（日K 永远够用），是分钟K 起的两个数量级跳变。
25 亿行/年的高频写入下，行存 + B-tree 索引的磁盘占用与 vacuum 膨胀不可持续。
因此按访问模式分层，而不是换一个库装所有。

**存储目标（2026-08-22 定）**：分钟K 与逐笔 tick 均要求**全量历史永久保留**，
不做滑动窗口删除。这决定冷层必须是「无限增长友好」的对象存储（腾讯云 COS），
而非本地固定容量盘。部署目标为腾讯云 CVM（1TB 数据盘，单机）。

## 三层拓扑

```
┌─────────────────────────────────────────────────────┐
│ 访问层（不变）：data-api 统一出口，三条铁律不变          │
│  读路由按数据类型分发到对应存储                          │
└──────┬──────────────┬───────────────────┬───────────┘
       ▼              ▼                   ▼
┌─────────────┐ ┌──────────────┐ ┌────────────────────┐
│ 热层 PG 16   │ │ 温层          │ │ 冷层                │
│ （现有）     │ │ ClickHouse   │ │ Parquet + COS      │
├─────────────┤ ├──────────────┤ ├────────────────────┤
│ 日K/报价/   │ │ 分钟K         │ │ 历史分钟K归档       │
│ 指数/宏观/  │ │ （在线 1 年） │ │ 逐笔 tick（写入即归档）│
│ 基本面/快照 │ │ 全市场技术指标│ │ 回测语料库         │
│ 业务榜单    │ │              │ │ （按年/市场分区）    │
├─────────────┤ ├──────────────┤ ├────────────────────┤
│ ~10 GB      │ │ ~150 GB      │ │ TB 级，无限增长      │
│ 毫秒级点查  │ │ 秒级聚合扫描  │ │ 离线批量读          │
└─────────────┘ └──────────────┘ └────────────────────┘
```

> 部署形态（CVM 1TB 单盘 + COS）：温层在线窗口 **1 年**；冷层以 **腾讯云 COS**
> 为主存（分钟K/tick 全量永久保留，无限增长），本地盘仅留可清空的工作缓存。
> 详见「单机部署适配（CVM 1TB + COS）」一节。

## 热层：PostgreSQL 16（现有，不动）

**承载**：日K、报价快照、指数、宏观、基本面、榜单、新闻——现有 24 张表全部。

**选型依据**：
- 访问模式是按主键/索引点查 + 小范围扫描（API 单标的读、榜单 Top N），B-tree 最优。
- UPSERT 幂等、事务、唯一约束——单一写者纪律需要关系型语义兜底。
- 运维现成，容量天花板 ~10 GB 无压力。

**备选排除**：MySQL（迁移零收益）；SQLite（并发写与服务形态不符）；Redis（缓存可做，持久层丢语义）。

**增长预案**：`daily_prices` 超 5000 万行（约 10 年全市场）时按 `(market, date)` 声明式分区（对应任务卡 4.3，仅预案不实施）。

## 温层：ClickHouse（单节点）

**承载**：分钟K（近 1-2 年在线窗口）、全市场技术指标宽表。

**选型依据**：
- 原生列存 + MergeTree，`ORDER BY (symbol, timestamp)` 排序键与行情访问模式（按 symbol 扫连续时间段）严丝合缝。
- 压缩比 10:1~20:1（行情数据高度规律），1.5 TB/年原始 → ~150 GB 实际。
- 批量块插（万行/块）吞吐百万行/s，collector 单进程足够喂饱。
- 单节点二进制即服务，HTTP 接口对接 data-api 现有 httpx 模式，无 JVM/集群协调。

**备选排除**：

| 候选 | 排除理由 |
|---|---|
| TimescaleDB | PG 扩展，行存本质不变；压缩靠后台 job，高频写入膨胀控制弱；超分区管理是额外心智负担 |
| InfluxDB | 社区版集群能力阉割；flux 生态窄；OHLC 场景无列存通用性优势 |
| QuestDB | 写入极强但生态薄，join/窗口函数覆盖面不如 CH |
| DuckDB | 嵌入式 OLAP（见冷层），不是服务型存储，不能做持续写入目标 + 并发查询源 |

**明确边界**：单节点即可，不上 Cluster（Keeper/副本是 10TB+ 规模的事）。

**分钟K schema 草案**：

```sql
CREATE TABLE minute_bars (
    symbol   LowCardinality(String),
    market   LowCardinality(FixedString(2)),  -- US/CN/HK
    ts       DateTime,                        -- K 线起始时间（交易所本地→UTC 统一）
    open     Float64,
    high     Float64,
    low      Float64,
    close    Float64,
    volume   UInt64,
    amount   Float64
) ENGINE = MergeTree
ORDER BY (symbol, ts)
TTL ts + INTERVAL 1 YEAR DELETE;              -- 在线窗口 1 年（CVM 单盘适配）；
                                              -- 归档管道先行迁 COS，TTL 兜底防超占
```

技术指标宽表同理（`ORDER BY (symbol, date)`，指标列按需展开）。

**降级路径**：资源紧张时可砍 CH，分钟K 全量直接落 Parquet + DuckDB 查——代价是交互式点查变慢，架构更简单。是可选项，非默认。

## 冷层：Parquet + 腾讯云 COS + DuckDB

三者各司其职，不是互斥选项：

### findb 一次性初始化与自有 data pool（2026-09-03）

findb 的 `thudata-1472715722/dist/full` 只作为一次性初始化输入，不作为运行时
数据库，也不保留供应商 DuckDB/tar.zst：collector 手动任务
`findb_pool_full` 按模块下载、校验、清洗并转换为自有 ZSTD Parquet，成功后删除
原始文件。prod 自有池位于宿主机 `/data/apps/tradeck/data-pool`（容器内
`/data/market-pool`）：

```text
data-pool/
  pool/                         # 不可变模块版本 + current 软链接
  bars/daily/asset=.../market=.../year=YYYY.parquet
  bars/minute/asset=.../market=.../symbol=.../year=YYYY.parquet
  staging/                      # 下载/解压/转换临时区，任务结束清空
```

`code/freq/type/...` 在导入时规范为 `symbol/frequency/security_type/...`，并追加
`source=findb`。复权因子按年分区；小型元数据镜像到 PostgreSQL 的
`instrument_master`、`data_coverage`、`instrument_name_history`、
`trading_suspensions`。A 股日K 后续由同花顺 `daily-k-10d` 每日更新 PG 与同一
Parquet 年分片；同花顺失败时 findb API 仅补 tracked A 股，避免单标的接口扫描
全市场导致 429。

**Parquet（存储格式）**：列存 + 压缩 + schema 自描述，按 `year=YYYY/market=XX/` 目录分区。回测扫特定年份/市场只读对应目录，天然谓词下推。

**腾讯云 COS（存储底座，主选）**：
- 成本：标准存储约 0.099 元/GB/月，按量付费无容量墙（本地云盘是预付费的墙，买 1TB 从第一天付 1TB）。
- 持久性：11 个 9 多副本。逐年积累的回测语料是项目最不可再生资产（历史分钟K/tick 数据源不会免费重拉），单盘本地目录在这件事上是裸奔。
- 访问模式匹配：回测是「批量读一批文件再算」，同地域 CVM↔COS 走内网，下行免费且快，延迟无感。
- 解耦：换 CVM/重装/迁移时，本地盘只剩无状态的热/温层，随时可弃；冷层在 COS 纹丝不动。
- 生态：完全兼容 S3 API（`endpoint_url` 指向 COS），DuckDB httpfs / boto3 直连。
- 存储级别用**标准存储**，不用低频——回测读取频率可能不低，低频有取回费。
- 备选：本地文件系统（最简，但容量有墙、无冗余）；自建 MinIO（单 CVM 场景是纯开销，放弃）。

**DuckDB（冷层查询引擎，内嵌在数据服务侧，不对外）**：嵌入式，**由 data-api/collector
进程内 `read_parquet()` 使用**，对外只经 REST 暴露结果（一年全市场分钟K 秒级扫描）；
零服务运维。
- 备选：Polars（DataFrame API 偏好场景可互换/共存——读的都是同一批 Parquet）。
- 读 COS 用 httpfs 扩展 + S3 兼容配置；数据服务侧可先把要扫的 year/market 分片拉到
  本地工作缓存再算（比 httpfs 直读稳）。
- **铁律边界（2026-08-25 更正）**：DuckDB/Parquet 是数据服务的**内部实现**，
  业务方（web/量化/回测）**不直接读 Parquet 文件、不持有 COS 凭据**——
  与「DB 永不对外」同一纪律；消费方唯一入口是 data-api 统一端口。

**Parquet 分区布局（COS bucket：tradeck-lake）**：

```
s3://tradeck-lake/
  minute_bars/
    year=2023/market=CN/part-000.parquet
    year=2023/market=US/part-000.parquet
    year=2024/market=CN/...
  tick/                      -- 逐笔（直接落冷层，不进任何在线库）
    year=.../market=.../date=.../symbol=....parquet
```

**分钟K 文件内排序（2026-08-22 定，回测点查性能关键）**：
分钟K Parquet 除按 `year/market` 目录分区外，**文件内必须按 `(symbol, ts)` 排序**写出。
否则单标的回测要把整个 `market/year` 分区（CN ≈ 3.3 亿行 / ~2GB）拉下来再过滤出
目标 symbol（6 万行 / 0.36MB），为 0.36MB 目标搬 2GB。按 symbol 排序后，DuckDB
可凭 row group 统计信息跳过非目标 symbol 的 row group（只读目标字节范围）。
这是 4.2a 建冷层管道时的 schema 决策，后改为迁移成本。

**单标的 1 年前分钟K 回测读路径与耗时**（详见「三层读实现与性能评估」）：
查询超出 CH 1 年 TTL 窗口 → 只能走冷层 Parquet。单标的 1 年 ≈ 6-10 万行 / 压缩后 <1MB。

| 阶段 | 首次（冷启动） | 后续（热缓存） |
|---|---|---|
| 现状（year/market 分区，文件内无序） | ~25-65s（拉 2GB 全分区再过滤） | ~1-3s |
| 文件内按 (symbol,ts) 排序（row group 裁剪） | ~5-15s（只读目标字节范围） | <500ms |
| 多标的批量（in 列表一次扫） | 与单只相同（一次扫全分区） | 同左 |

实务约定（数据服务侧）：data-api/collector 读冷层时可先把要扫的 `year/market` 分片
拉到本地工作缓存再算（比 httpfs 直读稳）；多标的批量查询用 `symbol IN (...)` 一次
扫全分区，不逐只查（逐只=重复扫全分区）。**业务方不直接做这些——它只调 data-api
的批量接口（如 `/api/bars/minute`），由数据服务侧完成冷层扫描并返回结果。**

**归档管道**：collector 侧定时 job 把 CH 中超窗口的数据导出为 Parquet 写 COS，再让 CH TTL 清除。归档产物是可校验的文件资产。**分钟K/tick 全量永久保留在 COS，任何层不做滑窗删除。**

**逐笔 tick 的存储定位**：tick 不进 PG、不进 CH，采集后**直接以 Parquet 落 COS**
（按 `year/market/date/symbol` 分区）。**tick 的读取同样只经 data-api**（数据服务侧
DuckDB 扫冷层，REST 返回给回测/研究），业务方不直读文件。
tick 是「写入即归档」的数据，没有在线查询价值——这是它与分钟K 的本质区别。

## 单机部署适配（CVM 1TB + COS）

**磁盘预算（1TB 数据盘，实际可用 ~900 GB）**：

| 用途 | 预算 | 说明 |
|---|---|---|
| 系统 + Docker 镜像 + 日志 | 100 GB | OpenBB 镜像不小，留足 |
| PG（热层） | 50 GB | 现 ~1 GB，10 年 ~15 GB，奢侈冗余 |
| ClickHouse（温层） | 250 GB | 分钟K 在线 **1 年**（压缩后 ~100-150 GB）+ 指标宽表 + 余量 |
| Parquet 本地工作缓存 | 100 GB | 数据服务侧扫冷层时拉分片的临时区，**可清空**，不是存储层 |
| 机动余量 | 400 GB | 备份暂存、导出、事故缓冲 |

**本地盘总占用锁死在 ~400-500 GB，永远健康**——COS 决策的最大红利：
冷数据无限增长（分钟K 全量 + tick 全量）全在 COS，以 ~0.1 元/GB/月计费，
不再是本地运维事件。

**COS 成本模型**（标准存储 0.099 元/GB/月，同地域内网下行免费）：

| 数据 | 年增长（压缩后估） | 5 年累计 | 5 年时月成本 |
|---|---|---|---|
| 分钟K 全量历史 | ~100-150 GB | ~750 GB | ~74 元 |
| 逐笔 tick 全量历史 | ~500 GB-1 TB | ~5 TB | ~500 元 |

注：tick 成本是大头。若成本敏感：可只落流动性前 N 标的的 tick；
或对超 2 年的 tick 转 COS 深度归档（约 0.01 元/GB/月，取回需小时级，
适合「极少读但绝不能丢」的老数据）。

**资源校核**：内存 PG ~0.5G + CH ~2G + OpenBB ~1.3G + 其余 ~1G——
**CVM 需 8G 内存起步（4G 需给 CH 显式限 max_memory_usage=2G）**；4C CPU 够用；
分钟K 每日批量写，普通 SSD 云盘即可。

## 三条铁律在新拓扑下的映射

1. **DB 永不对外**：PG/CH 的凭据与网络仅 collector、data-api 可见；**COS 密钥仅 collector（写）与 data-api（读）持有，业务方（web/量化/回测）一律不持有、不直读冷层文件**。
2. **单一写者**：写 PG、写 CH、Parquet 归档 COS 全部收敛在 collector 进程，沿用 datasource 门面限流与单进程纪律，不引入第二个写者。
3. **消费方只认 API**：data-api 路由屏蔽 PG/CH/Parquet 分布。**无例外**——回测/量化读冷层历史数据同样经 data-api（数据服务侧用 DuckDB 扫 Parquet 后 REST 返回），业务方不直读 Parquet、不持有 COS 凭据。DuckDB 是数据服务内部的冷层查询引擎，不是业务方的直连工具。

## 三层读实现与性能评估（2026-08-22 定，量化系统选型依据）

评估基准：2 万标的、分钟K 480 万行/日。三种典型读场景：

| 场景 | 查询形态 | 数据量级 | 谁在读 |
|---|---|---|---|
| S1 单标的近期点查 | `symbol=X AND ts >= 近5天` | ~2400 行 | 量化策略实时读 |
| S2 单标的长期扫描 | `symbol=X AND ts IN 近1年` | ~12 万行 | 策略研究/因子 |
| S3 全市场历史批扫 | `market=CN AND year=2020` | ~13 亿行 | 回测引擎 |

### 分钟K 三层读性能对比

| 维度 | PG（行存 B-tree） | CH（列存 MergeTree） | 冷层（Parquet+DuckDB） |
|---|---|---|---|
| S1 单标的近期 | 5-20ms ✅ | 5-30ms ✅ | 1-5s ❌ |
| S2 单标的 1 年 | 200ms-1s ⚠️ | 50-200ms ✅ | 2-10s ⚠️ |
| S3 全市场批扫 | 小时级 ❌ | 5-30s ✅ | 10-60s ✅ |
| 分钟K 写入 | 崩（WAL/vacuum/索引膨胀）❌ | 百万行/s 批量块插 ✅ | 追加文件 ✅ |
| 存储/年 | ~150GB ❌ | ~15GB（压缩 10:1+）✅ | ~15GB ✅ |
| 运维 | 重 | 单节点轻 | 零服务（COS+DuckDB） |

**结论**：分钟K 的读需求分解——量化策略在线读（S1/S2 近期窗口）走 **CH**（毫秒级，PG 给不了写入+S2）；回测批量扫历史（S3 全量）走**冷层 Parquet**（秒级，且永久）。**PG 彻底出局分钟K**（写入崩 + S3 死 + 存储爆），继续守日K/报价/宏观/基本面这些「百万行级 + S1 点查」的热层数据。

### 为什么分钟K 必须「CH + Parquet」双写（不能只靠一层）

- **不能只靠冷层**：量化策略的 S1/S2 在线读，冷层（文件粒度 + COS 冷启动）给不了毫秒级，必须有 CH 这个「有行级稀疏索引的在线列存」。
- **不能只靠 CH**：CH TTL 1 年会删数据，全量永久保存与跨多年历史回测要靠冷层；且冷层是 COS（11 个 9 + 无限增长 + 0.099 元/GB/月），比本地盘更适合做不可再生的历史资产。
- **双写时点**：每日采集时同一份数据 → ① 追加冷层 Parquet（永久真源）② 写 CH（在线窗口，可重建）。CH 崩了从 Parquet 重导，不丢数据。

### 各数据频率的读归属总结

- **日K 及以下频率**（日K/报价/宏观/基本面/榜单）→ 热层 PG，永久，唯一归宿。
- **分钟K** → 温层 CH（近期在线读，量化策略）+ 冷层 Parquet（全量永久 + 回测批扫），双写。
- **tick 逐笔** → 仅冷层 Parquet（写入即归档，无在线查询价值），回测经 data-api 读（数据服务侧 DuckDB 扫冷层，不直读文件）。

## 落地顺序（对应任务卡阶段四）

| 步骤 | 内容 | 触发条件 |
|---|---|---|
| 4.2a | 分钟K 采集 job + CH schema（上表草案）+ data-api `/api/bars/minute` 路由 | 量化需要分钟级回测时 |
| 4.2b | Parquet 归档管道（CH → COS）+ DuckDB 消费约定写入 docs | CH 逼近 1 年窗口时 |
| 4.2c | tick 采集 → 直落 COS（Parquet，year/market/date/symbol 分区） | 需要逐笔回测时 |
