# 分层存储设计 — 全市场全标的数据落地（阶段四最终状态）

> 阶段四「加固」的正式设计。前提：数据服务拆分（阶段一~三）已完成验收，
> 本文档定义全市场全频率数据落地时的存储拓扑。PG 不被替换，只做加法。
> 上游方案见 `docs/DATA-SERVICE.md`；任务卡见 `docs/TASKS-DATA-SERVICE.md` 阶段四。

## 设计前提与量级测算

以现有 universe 为底（CN 5528 + HK 2841 + US 11645 ≈ 2 万标的）：

| 数据类型 | 行/日 | 行/年（250 交易日） | 单行长 | 年存储（未压缩） | 10 年 |
|---|---|---|---|---|---|
| 日K（现有） | 2 万 | 500 万 | ~90B | 0.5 GB | 5 GB |
| 分钟K（1min） | ~1000 万 | 25 亿 | ~60B | 150 GB | 1.5 TB |
| 逐笔/tick（若做） | 5000 万-1 亿 | 百亿级 | ~50B | TB 级 | 10TB+ |
| 技术指标（全市场） | 2 万 | 500 万 | ~250B | 1.2 GB | 12 GB |
| 基本面/快照类 | 万级 | 百万级 | — | <1 GB | 可忽略 |

**核心判断**：PG 的死穴不是日K（日K 永远够用），是分钟K 起的两个数量级跳变。
25 亿行/年的高频写入下，行存 + B-tree 索引的磁盘占用与 vacuum 膨胀不可持续。
因此按访问模式分层，而不是换一个库装所有。

**存储目标（2026-08-22 定）**：分钟K 与逐笔 tick 均要求**全量历史永久保留**，
不做滑动窗口删除。这决定冷层必须是「无限增长友好」的对象存储（腾讯云 COS），
而非本地固定容量盘。部署目标为腾讯云 CVM（1TB 数据盘，单机）。

## 三层拓扑

```
┌─────────────────────────────────────────────────────┐
│ 访问层（不变）：data-api 统一出口，三条铁律不变          │
│  读路由按数据类型分发到对应存储                          │
└──────┬──────────────┬───────────────────┬───────────┘
       ▼              ▼                   ▼
┌─────────────┐ ┌──────────────┐ ┌────────────────────┐
│ 热层 PG 16   │ │ 温层          │ │ 冷层                │
│ （现有）     │ │ ClickHouse   │ │ Parquet + COS      │
├─────────────┤ ├──────────────┤ ├────────────────────┤
│ 日K/报价/   │ │ 分钟K         │ │ 历史分钟K归档       │
│ 指数/宏观/  │ │ （在线 1 年） │ │ 逐笔 tick（写入即归档）│
│ 基本面/快照 │ │ 全市场技术指标│ │ 回测语料库         │
│ 业务榜单    │ │              │ │ （按年/市场分区）    │
├─────────────┤ ├──────────────┤ ├────────────────────┤
│ ~10 GB      │ │ ~150 GB      │ │ TB 级，无限增长      │
│ 毫秒级点查  │ │ 秒级聚合扫描  │ │ 离线批量读          │
└─────────────┘ └──────────────┘ └────────────────────┘
```

> 部署形态（CVM 1TB 单盘 + COS）：温层在线窗口 **1 年**；冷层以 **腾讯云 COS**
> 为主存（分钟K/tick 全量永久保留，无限增长），本地盘仅留可清空的工作缓存。
> 详见「单机部署适配（CVM 1TB + COS）」一节。

## 热层：PostgreSQL 16（现有，不动）

**承载**：日K、报价快照、指数、宏观、基本面、榜单、新闻——现有 24 张表全部。

**选型依据**：
- 访问模式是按主键/索引点查 + 小范围扫描（API 单标的读、榜单 Top N），B-tree 最优。
- UPSERT 幂等、事务、唯一约束——单一写者纪律需要关系型语义兜底。
- 运维现成，容量天花板 ~10 GB 无压力。

**备选排除**：MySQL（迁移零收益）；SQLite（并发写与服务形态不符）；Redis（缓存可做，持久层丢语义）。

**增长预案**：`daily_prices` 超 5000 万行（约 10 年全市场）时按 `(market, date)` 声明式分区（对应任务卡 4.3，仅预案不实施）。

## 温层：ClickHouse（单节点）

**承载**：分钟K（近 1-2 年在线窗口）、全市场技术指标宽表。

**选型依据**：
- 原生列存 + MergeTree，`ORDER BY (symbol, timestamp)` 排序键与行情访问模式（按 symbol 扫连续时间段）严丝合缝。
- 压缩比 10:1~20:1（行情数据高度规律），1.5 TB/年原始 → ~150 GB 实际。
- 批量块插（万行/块）吞吐百万行/s，collector 单进程足够喂饱。
- 单节点二进制即服务，HTTP 接口对接 data-api 现有 httpx 模式，无 JVM/集群协调。

**备选排除**：

| 候选 | 排除理由 |
|---|---|
| TimescaleDB | PG 扩展，行存本质不变；压缩靠后台 job，高频写入膨胀控制弱；超分区管理是额外心智负担 |
| InfluxDB | 社区版集群能力阉割；flux 生态窄；OHLC 场景无列存通用性优势 |
| QuestDB | 写入极强但生态薄，join/窗口函数覆盖面不如 CH |
| DuckDB | 嵌入式 OLAP（见冷层），不是服务型存储，不能做持续写入目标 + 并发查询源 |

**明确边界**：单节点即可，不上 Cluster（Keeper/副本是 10TB+ 规模的事）。

**分钟K schema 草案**：

```sql
CREATE TABLE minute_bars (
    symbol   LowCardinality(String),
    market   LowCardinality(FixedString(2)),  -- US/CN/HK
    ts       DateTime,                        -- K 线起始时间（交易所本地→UTC 统一）
    open     Float64,
    high     Float64,
    low      Float64,
    close    Float64,
    volume   UInt64,
    amount   Float64
) ENGINE = MergeTree
ORDER BY (symbol, ts)
TTL ts + INTERVAL 1 YEAR DELETE;              -- 在线窗口 1 年（CVM 单盘适配）；
                                              -- 归档管道先行迁 COS，TTL 兜底防超占
```

技术指标宽表同理（`ORDER BY (symbol, date)`，指标列按需展开）。

**降级路径**：资源紧张时可砍 CH，分钟K 全量直接落 Parquet + DuckDB 查——代价是交互式点查变慢，架构更简单。是可选项，非默认。

## 冷层：Parquet + 腾讯云 COS + DuckDB

三者各司其职，不是互斥选项：

**Parquet（存储格式）**：列存 + 压缩 + schema 自描述，按 `year=YYYY/market=XX/` 目录分区。回测扫特定年份/市场只读对应目录，天然谓词下推。

**腾讯云 COS（存储底座，主选）**：
- 成本：标准存储约 0.099 元/GB/月，按量付费无容量墙（本地云盘是预付费的墙，买 1TB 从第一天付 1TB）。
- 持久性：11 个 9 多副本。逐年积累的回测语料是项目最不可再生资产（历史分钟K/tick 数据源不会免费重拉），单盘本地目录在这件事上是裸奔。
- 访问模式匹配：回测是「批量读一批文件再算」，同地域 CVM↔COS 走内网，下行免费且快，延迟无感。
- 解耦：换 CVM/重装/迁移时，本地盘只剩无状态的热/温层，随时可弃；冷层在 COS 纹丝不动。
- 生态：完全兼容 S3 API（`endpoint_url` 指向 COS），DuckDB httpfs / boto3 直连。
- 存储级别用**标准存储**，不用低频——回测读取频率可能不低，低频有取回费。
- 备选：本地文件系统（最简，但容量有墙、无冗余）；自建 MinIO（单 CVM 场景是纯开销，放弃）。

**DuckDB（查询引擎）**：嵌入式，回测进程内 `read_parquet()` 向量化扫描，一年全市场分钟K 秒级；零服务运维。
- 备选：Polars（DataFrame API 偏好场景可互换/共存——读的都是同一批 Parquet）。
- 读 COS 用 httpfs 扩展 + S3 兼容配置；**实务上推荐先拉本次要跑的 year/market 分片到本地工作缓存再算**，比 httpfs 直读更稳。

**Parquet 分区布局（COS bucket：tradeck-lake）**：

```
s3://tradeck-lake/
  minute_bars/
    year=2023/market=CN/part-000.parquet
    year=2023/market=US/part-000.parquet
    year=2024/market=CN/...
  tick/                      -- 逐笔（直接落冷层，不进任何在线库）
    year=.../market=.../date=.../symbol=....parquet
```

**归档管道**：collector 侧定时 job 把 CH 中超窗口的数据导出为 Parquet 写 COS，再让 CH TTL 清除。归档产物是可校验的文件资产。**分钟K/tick 全量永久保留在 COS，任何层不做滑窗删除。**

**逐笔 tick 的存储定位**：tick 不进 PG、不进 CH，采集后**直接以 Parquet 落 COS**
（按 `year/market/date/symbol` 分区），消费方只有回测/研究进程经 DuckDB 读。
tick 是「写入即归档」的数据，没有在线查询价值——这是它与分钟K 的本质区别。

## 单机部署适配（CVM 1TB + COS）

**磁盘预算（1TB 数据盘，实际可用 ~900 GB）**：

| 用途 | 预算 | 说明 |
|---|---|---|
| 系统 + Docker 镜像 + 日志 | 100 GB | OpenBB 镜像不小，留足 |
| PG（热层） | 50 GB | 现 ~1 GB，10 年 ~15 GB，奢侈冗余 |
| ClickHouse（温层） | 250 GB | 分钟K 在线 **1 年**（压缩后 ~100-150 GB）+ 指标宽表 + 余量 |
| Parquet 本地工作缓存 | 100 GB | 回测拉取分片的临时区，**可清空**，不是存储层 |
| 机动余量 | 400 GB | 备份暂存、导出、事故缓冲 |

**本地盘总占用锁死在 ~400-500 GB，永远健康**——COS 决策的最大红利：
冷数据无限增长（分钟K 全量 + tick 全量）全在 COS，以 ~0.1 元/GB/月计费，
不再是本地运维事件。

**COS 成本模型**（标准存储 0.099 元/GB/月，同地域内网下行免费）：

| 数据 | 年增长（压缩后估） | 5 年累计 | 5 年时月成本 |
|---|---|---|---|
| 分钟K 全量历史 | ~100-150 GB | ~750 GB | ~74 元 |
| 逐笔 tick 全量历史 | ~500 GB-1 TB | ~5 TB | ~500 元 |

注：tick 成本是大头。若成本敏感：可只落流动性前 N 标的的 tick；
或对超 2 年的 tick 转 COS 深度归档（约 0.01 元/GB/月，取回需小时级，
适合「极少读但绝不能丢」的老数据）。

**资源校核**：内存 PG ~0.5G + CH ~2G + OpenBB ~1.3G + 其余 ~1G——
**CVM 需 8G 内存起步（4G 需给 CH 显式限 max_memory_usage=2G）**；4C CPU 够用；
分钟K 每日批量写，普通 SSD 云盘即可。

## 三条铁律在新拓扑下的映射

1. **DB 永不对外**：PG/CH 的凭据与网络仅 collector、data-api 可见；COS 密钥仅 collector（写）与回测进程（读）持有。
2. **单一写者**：写 PG、写 CH、Parquet 归档 COS 全部收敛在 collector 进程，沿用 datasource 门面限流与单进程纪律，不引入第二个写者。
3. **消费方只认 API**：data-api 路由屏蔽 PG/CH 分布。唯一例外是回测侧 DuckDB 直读 Parquet 文件资产——读的是 collector 归档产出物，不是数据库连接，不违反铁律一。

| 步骤 | 内容 | 触发条件 |

**硬件量级**：腾讯云 CVM 4C8G + 1TB 数据盘可承载（本地 PG ~50 GB + CH ~250 GB + 工作缓存 ~100 GB，余量充足；冷数据全在 COS），无需集群。

**共同原则**：以上均为「需求真实出现再做」的加固件；在量化项目产生分钟级/全市场因子需求之前，不实施任何一项。
